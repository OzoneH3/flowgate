Bounded discovery — revised design only, NOT implemented support

Current implementation / release blocker
The manager and controller use SocketsLimited(1024). An over-limit or failed
dump is discarded, never used as a complete absence observation. Manager
discovery then fails; the controller census can fault and withdraw shaping.
Attribution hints do not cure the controller's census limit. Existing socket
coverage above that limit is not supported. The firewall path is unchanged.

Feasible progress contract
No finite resource budget can guarantee inspection of every socket regardless
of population or churn. This proposal supports only a finite, stable retained
population within explicit limits and successful dump/resolve service. Initial
DESIGN limits (unmeasured, subject to review before implementation): 4096 rows
per scan generation, 1024 rows per leaf dump, 512 shard descriptors, eight
examined rows per scheduling turn. Existing 128 binding / 16 cap limits remain.
The16-cap limit is validateConfig/MaxCaps in internal/uploadshape/manager.go.
These numbers are resource limits, not tested capacity or latency promises.
4096/8 alone is512 consumption turns: at one turn/second about8.5minutes,
before shard dump scheduling/retries. This is unacceptable as an invisible
application-wide activation delay and must remain explicit pending coverage.

A successful bounded shard dump becomes an immutable retained row snapshot.
Maintain a cursor and consume every row, including unusable/skipped rows, at
eight examined rows per turn. Only after all retained rows have been examined
may that shard be called examined. A completed dump alone is not discovery.
A shard's cursor never restarts because another dump changed ordering. Rows
are keyed by socket generation (cookie/inode/protocol/namespace plus tuple
where needed); a row is a hint, not authority. The existing fresh bind proof
must still validate current identity, socket generation and selected route.
A vanished/replaced row is rejected, never rebound by PID/tuple alone.

Port ranges can reduce dump size but cannot separate arbitrarily many sockets
on one port (SO_REUSEPORT/shared listeners/UDP). Splitting is bounded; an
unsplittable over-limit shard is OVERLOAD, not complete and not empty. Total
retained-row exhaustion is also OVERLOAD. No claim that port sharding alone
solves arbitrary populations. Alternative partitioning requires separate
kernel capability proof, not userspace filtering of an unbounded dump.

Scheduling and incomplete evidence
Rotate shard service fairly; consume bounded retained work without fixed-prefix
starvation. New sockets during consumption are discovered by attribution hints
or a later generation. Reordering between dumps cannot make retained rows
skip forward or reset the cursor. Interrupted/error/over-limit dumps discard
that dump's partial rows; bounded retries rotate rather than monopolize the
worker. Unresolved failed/overflow shards prevent a complete scan-generation
claim. Superseding cap configuration cancels affected pending work by version;
a row from an old generation must not silently configure a removed cap.

Conditional bound: for a stable finite snapshot with R retained rows and S
shards, consumption requires sum(ceil(rows_in_shard/8)) turns, plus successful
dump scheduling, resolution and retry work. Empty shards still require a dump.
There is NO unconditional wall-clock bound: slow helpers, errors, churn or
overload invalidate it. Under continuous churn there is no guaranteed discovery
of short-lived sockets. Fair generation rotation gives long-lived sockets an
opportunity within supported capacity, not a claim of continuous completeness.
A scan over separate-time dumps is not an atomic enumeration of current sockets.

User-visible coverage and cap application
CAS success acknowledges desired configuration only. Applying means controller
configuration has not reconciled. Once configured, Partial must distinguish:
configured caps; verified bound sockets; pending retained rows and shards;
failed/overloaded shards; latest progress time; oldest pending age; snapshot
examination time; and known unsupported/shared sockets. Do not call examined
rows bound, or a completed generation application-wide coverage. Unknown/new
sockets can escape; first-packet races remain. Report no application-wide cap.

Applying a cap to an already-running application can take many scheduling
turns. The previous 32–512-second cycle did not even include consuming more
than eight rows per shard and was not a valid bound. No such delay may appear
as an already-applied app-wide limit. Expose configured-but-discovery-pending,
Partial and overload explicitly. A priority scan for the newly configured app
could improve responsiveness but needs a separately reviewed, measured hint
source and fairness bound; it is NOT implemented by this proposal.

Controller pruning is a separate dependency
Exact per-binding socket existence queries might remove the controller's full
census dependency. Feasibility must first be proved for TCP/listeners, connected
and unconnected multi-peer UDP, shared sockets and socket cookies. Errors must
not become evidence of a different owner; failure/lease behavior must remain
explicit. Compare CPU, elapsed time and syscall count against bounded census
at several binding/population sizes. No claim these lookups are cheaper.
Sharded manager discovery alone cannot close the controller's 1024-row limit.

Required proof before implementation acceptance
Stable population: retained last row eventually examined, all rows consumed,
no prefix starvation; more than eight rows in one shard; multiple capped apps.
Overload: >1024 same-port sockets and >total retained capacity; truthful Partial
and bounded memory/work; no class inherited by an ambiguous socket.
Churn/reordering/interrupted dumps: no false completion/absence, bounded retry,
no stale-generation bind; cap add/remove/version races; observed pending delay.
Controller lookup feasibility and comparative cost; resource exhaustion and
lease withdrawal; actual daemon receiver/cap/Deny tests in isolation.

This is a reviewed-design candidate only. No sharding, cursor, new limits,
exact lookup or coverage fields described here are implemented in this round.
