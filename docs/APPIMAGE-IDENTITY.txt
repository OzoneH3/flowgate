Persistent native AppImage identity
=================================

A random FUSE mount directory is not a stable executable location. For a
supported self-mounting runtime, FlowGate uses a separate application-key domain:
UID + canonical archive pathname + executable path relative to the mounted root.
Each inner executable remains independent. Another archive path, even containing
identical bytes, and another UID do not inherit a permission. Incoming/outgoing,
rule scopes, revisions and update-following policy retain their existing meaning.
No display name, parent process, mount label or environment value is authority.

Supported evidence
------------------
This implementation supports the x86_64 AppImageKit effcebc type-2 runtime whose
first 188392 bytes, with the four fixed packaging-metadata ranges below zeroed,
have SHA256:
24da8e0e149b7211cbfb00a545189a1101cb18d1f27d4cfc1895837d2c30bc30
This is a runtime implementation pin shared by different applications, not an
application allow-list. A SquashFS superblock must immediately follow that prefix.
For this exact layout only, normalize .digest_md5 (175704,16), .upd_info
(175720,1024), .sha256_sig (176744,1024), and .sig_key (177768,8192).
All ELF/program/section headers, offsets, flags, loaded runtime code/data and
remaining bytes stay pinned. These fields are package metadata, not runtime code
or permission/signature authority. No section names from an untrusted file select
what is ignored. Runtime signature authentication is not claimed.

The target remains a verified native executable. Existing owner-credential FUSE
metadata checks, mapped device/inode and process-generation bookends still apply.
Its owner-only FUSE mount must be a read-only whole-filesystem mount. Kernel
fdinfo fuse_connection binds that mount's device to its live transport holders.

Every process's task FD tables are examined, including private non-leader tables.
KCMP_FILES can prove shared tables, which are scanned once; every member of a
matching table still needs its own provider validation. Anonymous kernel objects
are excluded from FUSE fdinfo parsing; all other FD records remain checked.
Transient per-FD disappearance before finding a matching holder permits at most
two complete table retries, charged to the same budget and generation-bookended.
A known-holder failure, unreadable record or exhausted retry stays inconclusive.
Unknown holders are refused, not skipped. Each holder must execute the supported
runtime from the canonical archive inode and hold that same archive open. Other
readable regular-file inputs (including stdin) are refused. The validated reader
retains its input descriptor while serving FUSE; TARGET_APPIMAGE selecting a
different archive therefore does not acquire the first archive's permission.

Executable mappings must match their backing bytes. Archive executable mappings
must be the single supported non-PIE mapping (0x400000..0x42b000, file offset 0).
Its last page includes packaging metadata as page padding: not every executable-
mapped byte is hash-pinned. The validated runtime uses those fields as metadata,
not as an input-reader implementation or execution target. Additional/relocated
archive executable mappings are refused. This does not attest against a debugger
redirecting control flow into existing padding. On filesystems such as Btrfs,
a maps/stat device mismatch requires the kernel map_files entry to prove the
same mapped file; inode equality alone is insufficient. Other mappings must be
root-owned, not writable by non-root users, have protected parent directories,
and represent the supported libc/loader/libfuse/libz/libdl/libpthread/librt roles.
Anonymous/injected code and unrelated preload libraries are unsupported. Kernel
vdso/vsyscall mappings are the explicit kernel-code exceptions.

Full holder discovery is repeated independently before and after the observation.
There is no positive locator or identity cache. A missing/unreadable/changing
observation, unknown runtime, private/delegated unknown holder or discovery-budget
exhaustion falls back to the existing per-mount native identity, with the reason
included in executable evidence. It does not create an automatic Allow.

Limits and migration
--------------------
Existing temporary-path rules are not guessed or migrated. A user needs one new
saved permission for the stable identity. A temporary/once Allow remains temporary.
Moving the archive to a different canonical path creates a new identity. Updates
at the same path follow the existing explicit update-following rule contract.

This covers native executable files inside the supported mount. It does not add
stable script identity for an external Python/shell interpreter, extracted
AppImages, arbitrary FUSE servers or unvalidated runtime prefixes. Older kernels
without fuse_connection reporting retain the old identity. A changed runtime
prefix may require additional implementation validation before being supported.

Observations are bounded, live snapshots, not an atomic freeze of the system or
an anti-debugging attestation. A same-UID debugger can change process memory or
transfer descriptors later, as with ordinary native process evidence. Unrelated
FD churn or a large task population can make discovery inconclusive; the explicit
fallback may still cause a new prompt. No cache hides that missing evidence.

Validation scope
----------------
Disconnected guest tests use distinct synthetic archives, separate UIDs, separate
inner executables and multiple random mounts. Independent receiver tests exercise
saved Allow/Deny, relaunch, daemon restart in the guest and revocation. API-driven
Remember tests do not prove native GUI behavior or persistence of a once Allow.
No installed-host migration or deployment is implied by these tests.
