Experimental native upload integration (disabled by default)

Scope
This daemon integration builds on isolated M1, not a host release. Only one
explicit startup-selected supported interface in a disposable child network namespace is
supported. Host physical-interface activation, download, VPN/tunnels, priorities
and UI are deferred; isolated NIC scope is in UPLOAD-SHAPING-PREFLIGHT.txt.
The installed25db release/updater allowlist is unaffected.

Root startup opt-in (actual serve path, isolated guest only)
 --experimental-upload-interface <supported-interface>
 --experimental-upload-helpers <absolute root-owned build directory>
 --experimental-upload-state <absolute private controller journal directory>
 --experimental-upload-parent-netns 'net:[parent inode]'
 --administrator (with the existing selected API UID)
The current namespace must differ from that explicit parent. This is an
experimental deployment guard, not protection against a malicious root lying
about the parent. Trusted helper files and all ancestors must be root-owned,
not symlinks or writable by non-root. Startup installs only the API capability;
it does not activate shaping. No shaping worker, poll, helper or attachment
exists while disabled in a clean state. Existing unrelated daemon observers
are unchanged.

API contract for the UI owner
Capability: experimental-native-upload-v1. Existing authenticated private Unix
API, SO_PEERCRED; root or the explicitly configured administrator only.
The administrator can read status through the read-only companion, but cannot
configure through it. Ordinary users cannot
read machine shaping state or mutate it. No request selects helper paths or
expands the startup interface. All requests include version:1 and generation
from the current daemon list response. Example reads:
 {"version":1,"operation":"upload-status","generation":"CURRENT"}
Response.upload_shaping contains version (initial1), applied_version, enabled,
interface, status, configured_caps, kernel, known_gaps, last_error, updated,
verified_until, coverage_snapshot_expired, coverage, application_wide_guarantee:false.

Full replacement desired configuration, not a patch:
 {"version":1,"operation":"upload-configure","generation":"CURRENT",
  "expected_version":1,"upload_config":{"enabled":true,"caps":[
   {"uid":1000,"application":"VERIFIED_NATIVE_APPLICATION_KEY",
    "bits_per_second":4000000}]}}
Maximum16 distinct UID/application targets;1..1000Mbit/s each. Application keys
come from existing verified application observations; a configured key alone
never binds a socket. Caps aggregate across freshly bound sockets/processes.
No automatic parent/helper/launcher inheritance. An empty enabled cap list removes
caps but leaves the opted-in controller; disabling requires caps:[]:
 {"version":1,"operation":"upload-configure","generation":"CURRENT",
  "expected_version":2,"upload_config":{"enabled":false,"caps":[]}}

Configuration is session-scoped, deliberately not persisted. Daemon restart
requires a new reviewed configuration, never a replay of old socket bindings.
Generation mismatch => stale_generation; missing conditional fields/invalid
rates => invalid_request; old version => stale_version; unauthorized/companion
write => forbidden; absent startup capability => unavailable.

Acknowledgement means desired version accepted, normally Applying, NOT that
traffic is capped. Follow upload-status until applied_version matches and inspect
coverage/faults. Kernel changes are serialized asynchronously; partial kernel
failure does not roll desired state back and can leave earlier changes applied.
Unsupported + last_error reports failure; submit a new reviewed CAS to retry or
remove. An in-flight operation from the old version may finish before the new
version is processed; Applying is not instantaneous enforcement. No permission
mutation is involved. On lost reply, read generation/version/configuration and
reconcile. Never blindly replay or advance expected_version behind a draft; a
replay with the old version is rejected. A newer desired state may have already
superseded the lost request.

Coverage and accepted ownership
One socket cookie is assigned to its freshly verified native application when
bound, until close/removal or explicit fresh revalidation/rebinding. Exec, fork
and descriptor transfer AFTER binding do not automatically change its class.
The API does not currently offer an explicit rebind operation; removing the cap
and reconfiguring causes fresh discovery. Unknown or ambiguous initial ownership
never inherits another application's class. Runtime/Wine/shared sockets that
cannot satisfy the native M1 proof remain uncovered.

Configured caps, kernel app classes, requested bindings and covered_bindings
are distinct. Kernel status/limitations describe only its requested subset.
The daemon's enabled state is conservatively Partial, even if the kernel subset
says Active: this integration cannot enumerate/cap every new application socket
before first traffic. Applying means reconciliation is pending; Unsupported
means a fault/capability/ownership refusal. Disabled means clean shutdown; an
orphan journal at startup is Unsupported, not silently called Disabled.

Attribution publishes bounded nonblocking hints; a private helper repeats the
full M1 socket/holder/process proof before binding, matching expected app/cookie.
Queued hints never become permission evidence. Existing connected sockets are
discovered independently of the GUI/UDP collector: max4096 retained socket rows, at most8
candidate inspections and512 cheap row examinations per scheduling turn. Progress
is retained across cap edits; errors back off to30s. See discovery_snapshot for
pending rows and overload, not an application-wide completion flag. Kernel creator UID is
a discovery filter; a socket whose current owner UID differs may need an actual
attribution hint. Unconnected/listening/wildcard rows without a usable peer are
reported as gaps and need an outgoing attribution observation. TCP endpoint-rule
shortcuts may be covered only after connection discovery. First packets and
traffic before discovery/verification use default/unclassified handling and are
NOT retroactively capped. Route changes to another interface escape this cap.

known_gaps counts observations/failed attempts/controller generations, NOT lost
packets or unique missing sockets. In particular first_packet_binding_race counts
controller starts, not the number of escaped packets. Kernel counters index0 =
unbound/default,1 = classified,17 = expired;2..16 reserved. They include unrelated
and control traffic, not a per-app uncovered-byte estimate. Kernel map verification
has an explicit lease-derived verified_until, conservatively anchored before the
status RPC. The published verified_until is wall-clock display information; the
daemon uses its retained monotonic deadline for expiry. Clients should use the
returned coverage state rather than make authority decisions from local clocks. After that, covered_bindings is returned as0/Partial until renewed
status is observed; the cached observation is never advertised indefinitely.

Bounds and failure handling
128 bindings/hints;16 concurrent classes; max4096 retained discovery rows; finite helper
command deadlines. IDs1..65533 are monotonically allocated and never reused in
one generation, even after retirement, so an old queued priority cannot name a
new application's class. The former16-generation lifetime restriction is gone.
At ID-space exhaustion the manager verifies owned cleanup, rotates the whole
controller and rediscovers fresh bindings automatically. This creates an explicit
Partial gap; failed cleanup stops instead of deleting foreign objects.

M1 five-second kernel heartbeat/binding leases, bounded queues, idle class
retirement and foreign-object verification remain. Controller death/renewal loss
lets shaping expire to default, NOT firewall Allow. Ordinary disable closes the
helper and verifies cleanup. Fault->disable uses a journal-triggered cleanup-only
helper that never creates attachments; absence of journal creates no helper.
Cleanup failure/timeout/foreign change stays Unsupported and requires a new CAS.
Startup orphan journals are reported, with no implicit helper or stale restoration;
explicit disable requests cleanup. If the selected interface vanished or was
replaced, cleanup refuses; restoring the original owned interface identity permits
verified cleanup. Otherwise manual review of orphan pins/journal is required.
No blind deletion by interface name; no atomic CAS against concurrent root edits.

Evidence / remaining physical-interface work
Actual serve guest proof and retained failures: .workspace/shaping-integration/
M0/M1 receiver, shared/transfer/socket reuse, bounded queues and foreign-object
proofs are reused where unchanged. Test fixture: experimental/upload-shaper/
integration/run.py. All kernel experiments are capped disposable VM only.

Before a host-ready release:
1. Define safe coexistence with real NIC default fq_codel/mq and existing TC/BPF;
   current controller explicitly refuses them. Never replace foreign root TC.
2. Validate real NIC offloads/GSO/TSO, retransmission/accounted bytes, IPv4/IPv6,
   multiqueue hardware, throughput and CPU/latency at realistic rates.
3. Validate device removal/recreation/rename, namespace/routing changes and orphan
   cleanup UX without weakening identity/generation checks or deleting foreign TC.
4. Package root-trusted helper identities and permissions, audit crash windows,
   configuration durability choices and administrator-facing partial coverage.
5. Review exact candidate and obtain host activation approval. No current release
   or updater approval is implied by this experimental integration.

NIC preflight increment: see docs/UPLOAD-SHAPING-PREFLIGHT.txt. The namespace guard

Kernel status may include compatibility (topology, supported, reasons, offloads,

Observation-age interval (correctness increment, experimental)
The nested kernel.verified_age_ms / kernel.verification fields are the immutable
controller observation at report creation. Top-level verification_age_min_ms
and verification_age_ms bracket the age SINCE VERIFICATION START at API read
time. The compatibility field verification_age_ms is the conservative UPPER
bound, not an exact timestamp. observation_rpc_ms is rounded-up RPC duration;
observation_held_ms is rounded-down time since response receipt. All calculations
use retained monotonic anchors, not JSON wall times. Missing/invalid observations
remain unknown with no age; reads never upgrade the controller label.

A report's millisecond age was floored at an instant between request and receipt:
lower = reported age + floor(time since receipt)
upper = reported age + 1ms + ceil(time since request)
The interval makes transport uncertainty explicit instead of hiding double-counted
RPC time in an apparently exact age. The upper bound still drives the unchanged
1s/2s fresh/stale/unknown labels. Fractions near a boundary can classify
conservatively; this is not a threshold widening or a claim of more fresh samples.

These labels describe observation RECENCY only. They are not a controller
liveness result, and are not binding leases or permission authority. Existing
verified_until / coverage_snapshot_expired independently describe the conservative
lease observation; expired coverage reports zero covered bindings. Applying and
Unsupported remain unchanged by read-time aging. A controller report with a
verification-start age over5s now reports Partial, zero confirmed coverage
and an explicit observation-watchdog limitation. It does not latch a daemon
fault merely because an observation is old. Actual ownership/controller faults
remain Unsupported. The upper age may be up to2ms larger than the prior
formula because it now includes integer-floor uncertainty and rounding.

Priority discovery (experimental, see UPLOAD-SHAPING-PRIORITY.txt):
priority_discovery records version, hint_inodes, pending_rows, attempts,
incomplete/reason, hint_duration_ms, completed. Completion describes a bounded
hint attempt only, never application-wide coverage. Configuration accepted,
applied_version, verified bindings and receiver cap enforcement are distinct.
Kernel maintenance timing fields are observation counters only:
maintenance_cycles, maintenance_pass_ms, max_maintenance_pass_ms,
max_completion_gap_ms, max_renewal_span_ms (controller-lifetime maxima).

Experimental GUI integration
snapshot.deployment_mode is isolated or host-trial; startup selects this mode,
not the API. host-trial requires the explicit experimental startup switch and
an explicitly selected structurally supported single-queue interface. The
normal updater neither selects this mode nor authorizes this release.

snapshot.coverage_valid_for_ms is remaining monotonic coverage time at API
read (0..5000), rounded down. A client anchors it at request START and zeros
coverage when it elapses. kernel.valid_for_ms is part of a retained controller
observation and MUST NOT be treated as remaining time on each API read.
Each kernel.bindings entry has covered (report-only), derived from the same
health sample as covered_bindings. Expiry/fault/Disabled/Unsupported clears
both the aggregate and per-binding flags in the returned snapshot. These
fields are reporting, never permission or binding authority.

Directional extension (experimental-native-download-v1)
------------------------------------------------------
The existing upload-status/upload-configure operations remain the single service.
A configured cap now contains bits_per_second (upload;0 means absent) and optional
 download_bits_per_second (0/absent means absent). At least one must be nonzero;
each nonzero direction is1,000,000..1,000,000,000bit/s. One application/UID entry
holds both; duplicate application entries remain invalid. CAS replaces the full
configuration, so directional clients must preserve the other rate.

The opt-in daemon advertises experimental-native-download-v1 alongside upload.
Old upload-only daemons must not receive download edits. Kernel status includes
 download adapter observations, and each binding has download:boolean. This is
TCP-direction eligibility, not current coverage: require covered=true and a live
coverage snapshot as well. No change to permission identity, fresh binding proof,
lease duration or manager ownership. See DOWNLOAD-LIMITER.txt for explicit gaps.

Traffic priority extension (experimental-traffic-priority-v1)
 Cap.traffic_priority: "low" | "high" (omitted/"normal" = Normal), one value for both directions.
 upload_config.schema = 2, upload_budget_bits_per_second, download_budget_bits_per_second
 (0 = none, 16..10000 Mbit/s). schema 2 is required when the request or the stored config has a
 budget or priority (else schema_upgrade_required); unadmittable floors -> allocation_below_minimum.
 A cap entry is valid with any cap or a non-Normal priority. Budget-only enabled configs are allowed.
 Snapshot adds upload/download_budget_bits_per_second; kernel.traffic_priority reports budgets,
 applied tuples, default class and evidence counters; bindings add upload_class/download_class
 (direction eligibility; AND with covered and snapshot expiry). See docs/TRAFFIC-PRIORITY.txt.
