# Scripts

Run commands from the repository root. Build output, caches and disposable
fixtures belong in `.workspace/`.

| Location | Purpose |
| --- | --- |
| `build.sh TARGET` | Build the backend helpers, Windows fixtures or desktop clients. |
| `run-*.sh`, `demo-desktop.sh` | Launch development clients or the desktop demo. |
| `check.sh` | Go, Python, Electron and Qt checks plus isolated receivers; `--wine` adds Wine. |
| `checks/` | Focused check runners and mocked deployment tests. |
| `acceptance/` | Isolated integration scenarios, their peers and shared fixture modules. |
| `prepare-release.sh` | Prepare immutable artifacts without installation. |
| `install-prepared.py`, `update-and-start.sh` | Explicit installation/update operations. |
| `*-essentials.py`, `*-system-networking.py` | Essential-networking review and diagnostics. |
| `update-address-registry.py` | Refresh the versioned address registry. |
| `lab.sh`, `go-env.sh` | Private namespace launcher and workspace cache setup. |

Examples:

```sh
scripts/check.sh
scripts/checks/check-electron.sh
scripts/checks/check-runtime.sh
scripts/lab.sh python3 scripts/acceptance/process-rules-isolated.py --help
```

`acceptance/*_acceptance.py` and `*_cases.py` are support modules imported by
scenario runners. `acceptance/provenance-sim/` contains explicitly simulated
launcher fixtures, not production launch wrappers. Keep their sibling imports
together. Python runners in subdirectories resolve the repository two levels up.

Some checks require Wine, Qt/Wayland, collectors or an explicitly authenticated
private namespace. Read the runner before invoking it. `evaluate-host.sh`,
installation commands and essential-permission application can affect the host;
folder organization does not authorize those operations.

Legacy `scripts/check-*.sh` / fixture paths have moved into `checks/` and
`acceptance/`; repository callers and documentation use their new locations.
For direct Python checks, keep generated bytecode in the workspace:

```sh
export PYTHONPYCACHEPREFIX="$PWD/.workspace/python-cache"
python3 scripts/checks/test-install-monitoring.py
```

## Build and prepare

```sh
scripts/build.sh desktop
scripts/build.sh electron
scripts/build.sh windows wine-table
scripts/build.sh tcp-initiation udp
scripts/prepare-release.sh                 # matched backend and Electron bundle
scripts/prepare-release.sh --backend-only  # backend bundle only
```

The build command accepts one or more explicit targets. Collectors and Wine
helpers are built only when requested. `--help` lists the targets. Preparation
requires clean master, checks an existing bundle before reusing it, and never
installs or activates protection. Backend and GUI bundles retain their existing
`.workspace/daily-releases/` and `.workspace/automatic-zone-releases/` locations.

The old separate build/release scripts have been replaced by these two entry
points. The superseded installer that mixed installation and live acceptance,
and its tests, have been removed. The current monitoring installer, rollback
tests, and separate acceptance scenarios remain.

## One-command update and start

```sh
scripts/update-and-start.sh
```

The normal command fast-forwards master when upstream is configured, then selects
the exact SHA in `deployment/default-release`, not HEAD. It requires already
prepared matched artifacts and verifies them. `deployment/release-policy.json`
rejects experiments and refuses every unapproved SHA before contacting the host,
including direct calls to the Python coordinator. Approval is an explicit exact-SHA
review; preparing a bundle does not approve installation. The current pin remains
`25dbb1a90e81f6fc2a150231cae699db87e430f3`; rejected `66313d5` is blocked.
The coordinator authenticates sudo before interrupting
protection, stops protection if a daemon update is needed, installs, verifies
the running build, restores the previous protection mode, then closes the old released GUI
and launches the matching GUI. It preserves stored rules and existing Wine
observer configuration. Running it again with the same healthy daemon skips
installation and the protection interruption.

Upstream access is noninteractive and limited to 60 seconds, plus up to five
seconds to kill stuck child processes. A fetch failure stops before preparation
or any installed-service action; it never silently uses an older local revision.

Options:

- `--profile preserve` (default): restore the mode selected before the update; new installs stay monitoring.
- `--profile incoming` or `--profile monitoring`: select Incoming or leave protection off.
- `--profile both --acknowledge-outgoing-blocking`: explicitly enable outgoing default-deny after reviewing Essential networking and recovery. Without acknowledgement, a transition from another mode refuses before authentication, stop or installation. DNS/DHCP/VPN can be blocked; no automatic permissions or continuous countdown are added. The warning adds one read-only evidence line from the current daemon: the number of stored Essential preset records (which may include disabled or expired rules) with the current discovery revision, "No stored Essential preset records" or "status unavailable"; none of these validates coverage.
- `--no-gui`: perform the same update/protection workflow without switching the GUI.
- `--recover-stopped`: recover an unavailable daemon into monitoring only.
- `--local`: skip upstream access; keep the approved release pin (still requires a clean tree).
- `--wine-discovery`: explicitly enable generic supported Wine discovery.
- `--dry-run`: show the plan without fetching, building, authenticating, changing protection or signalling the GUI.

A lost control acknowledgement is checked through a fresh status read; the
mutation is not replayed. Installation or build verification failure stops the
workflow before activation or GUI switching. The monitoring-only installer itself
continues to leave protection stopped; the launcher performs the explicit start.
Read-only status checks and mocked workflow tests live in
`lib/update_and_start.py` and `checks/test-update-and-start.py`.

## Real lwp / Proton failure reproduction

`checks/check-proton-launcher.sh` runs two Windows applications through the actual
`lwp` / Python / UMU / pressure-vessel / Proton chain in private namespaces.
See [the reproduction guide](../docs/PROTON-LAUNCHER-REGRESSION.md) for inputs and
meaning of the results. Success means the known attribution failure was
reproduced and receiver controls passed; it does not mean the failure is fixed.

## Installer trust and recovery

Use `python3 scripts/install-prepared.py --bundle PATH` for a monitoring-only
installation, or `update-and-start.sh` for the complete update workflow. The
coordinator snapshots and verifies the selected bundle before authentication.
Root receives those bytes on stdin, stages them in a private root-owned directory,
and uses `/usr/bin/python3 -I`. It does not import modules or execute the installer
from the writable build folder. This trusts the selected local checkout; the
manifest is an integrity check, **not** a publisher signature. Do not run a bundle's
Python installer directly with sudo.

`--recover-stopped` recovers an unavailable daemon in monitoring mode only.
After successful recovery, run the normal update command to start protection.
If an install fails before replacement and the original daemon generation/build
is still running, the coordinator restores its prior protection mode.

If startup or verification fails after replacement, the installer stops the
failed writer and removes its interception. It verifies the retained previous
release and backup hashes, preserves failed database files under the evidence
folder, and restores the previous executable, stopped-writer database snapshots,
configuration and unit files together. Backup failures before replacement restart
and verify the unchanged old daemon. Stale SQLite WAL/SHM/journal files are
removed before the old daemon starts. The restored daemon must pass build, rules,
process and monitoring verification before the updater restores the protection
mode that was active before the update. A standalone monitoring installer leaves
the restored daemon in monitoring. The update still exits with failure and does
not switch the GUI to the failed build.

Concurrent installers are refused. A first installation, an unverifiable previous
release, failed rollback, or an interruption/power loss can still require manual
recovery. Failed rollback leaves the service stopped/disabled and reports the
backup directory. Use `--recover-stopped` for guarded monitoring-only recovery,
then explicitly start protection. Edits or logs created by the failed new daemon
remain in `failed-state`; rollback restores the state captured immediately after
the old daemon stopped.

New installations select the invoking sudo user's UID. Existing installations
retain their configured administrator; installations from before the configuration
file retain their historical UID 1000. Root-owned
`/etc/flowgate/administrator.json` records this choice.

Release preparation builds both collectors from source and runs current Go race
and vet checks. It no longer depends on another developer's historical evidence
folders or a particular collector binary hash. These checks do not establish
live-kernel collector compatibility or native desktop behavior on a new host.

`check.sh` now includes Go vet, Go race tests in a private network namespace,
isolated native receivers, mocked deployment
checks, Electron build/tests, and Qt offscreen desktop/snapshot tests. Wine remains
opt-in with `--wine`. Private mount/runtime and essential-networking checks run in private namespaces.
The subordinate-ID user-namespace fixture is still separate and explicitly
reported as not covered by the default command. Required build dependencies must be installed; missing
dependencies fail the command rather than silently skipping a suite.

The native ownership/API fixture tests require a disposable PID/network namespace;
plain `go test` reports an explicit skip for those tests outside that environment.
The lab assertions still require a real owned socket. A host census with inaccessible
processes or changing holders is a visibility result, not a portable unit-test fixture.
Release acceptance must run the gated cases and the ordinary-UID API cases explicitly;
a skipped native case is not evidence that ownership or delivery worked. Use capped
VM validation for kernel/native work in this development environment.
