# Scripts

Run commands from the repository root. Build output, caches and disposable
fixtures belong in `.workspace/`.

| Location | Purpose |
| --- | --- |
| `build-*.sh` | Build the backend helpers, Windows fixtures or desktop clients. |
| `run-*.sh`, `demo-desktop.sh` | Launch development clients or the desktop demo. |
| `check.sh` | Main Go race tests and native isolated receiver checks; `--wine` adds Wine. |
| `checks/` | Focused check runners and mocked deployment tests. |
| `acceptance/` | Isolated integration scenarios, their peers and shared fixture modules. |
| `prepare-*-release.sh` | Prepare immutable artifacts without installation. |
| `install-*.py`, `update-and-start.sh` | Explicit installation/update operations. |
| `*-essentials.py`, `*-system-networking.py` | Essential-networking review and diagnostics. |
| `update-address-registry.py` | Refresh the versioned address registry. |
| `lab.sh`, `go-env.sh` | Private namespace launcher and workspace cache setup. |

Examples:

```sh
scripts/check.sh
scripts/checks/check-electron.sh
scripts/checks/check-runtime.sh
scripts/lab.sh python3 scripts/acceptance/process-rules-isolated.py --help
```

`acceptance/*_acceptance.py` and `*_cases.py` are support modules imported by
scenario runners. `acceptance/provenance-sim/` contains explicitly simulated
launcher fixtures, not production launch wrappers. Keep their sibling imports
together. Python runners in subdirectories resolve the repository two levels up.

Some checks require Wine, Qt/Wayland, collectors or an explicitly authenticated
private namespace. Read the runner before invoking it. `evaluate-host.sh`,
installation commands and essential-permission application can affect the host;
folder organization does not authorize those operations.

Legacy `scripts/check-*.sh` / fixture paths have moved into `checks/` and
`acceptance/`; repository callers and documentation use their new locations.
For direct Python checks, keep generated bytecode in the workspace:

```sh
export PYTHONPYCACHEPREFIX="$PWD/.workspace/python-cache"
python3 scripts/checks/test-install-monitoring.py
```

## One-command update and start

```sh
scripts/update-and-start.sh
```

The normal command fast-forwards master when upstream is configured, prepares
and verifies the matched release, authenticates sudo before interrupting
protection, stops protection if a daemon update is needed, installs, verifies
the running build, starts **Both** protection, then closes the old released GUI
and launches the matching GUI. It preserves stored rules and existing Wine
observer configuration. Running it again with the same healthy daemon skips
installation and the protection interruption.

Options:

- `--profile preserve`: restore the mode selected before the update (including monitoring/off).
- `--profile incoming` or `--profile monitoring`: select Incoming or leave protection off.
- `--no-gui`: perform the same update/protection workflow without switching the GUI.
- `--dry-run`: show the plan without fetching, building, authenticating, changing protection or signalling the GUI.

A lost control acknowledgement is checked through a fresh status read; the
mutation is not replayed. Installation or build verification failure stops the
workflow before activation or GUI switching. The monitoring-only installer itself
continues to leave protection stopped; the launcher performs the explicit start.
Read-only status checks and mocked workflow tests live in
`lib/update_and_start.py` and `checks/test-update-and-start.py`.

## Real lwp / Proton failure reproduction

`checks/check-proton-launcher.sh` runs two Windows applications through the actual
`lwp` / Python / UMU / pressure-vessel / Proton chain in private namespaces.
See [the reproduction guide](../docs/PROTON-LAUNCHER-REGRESSION.md) for inputs and
meaning of the results. Success means the known attribution failure was
reproduced and receiver controls passed; it does not mean the failure is fixed.
