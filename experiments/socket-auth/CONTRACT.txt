The background scheduler admits only ordinary application-rule Allow outcomes;
Deny/Ask/Once/lease/preset outcomes do not start background verification. Up to
64 flows, eight grants per application and two concurrent full verifications
are retained. Renewal is scheduled from the preceding start plus 100 ms, with
an earliest-due timer capped at 25 ms and completion/new-flow wakes; no
same-flow overlap. Selection uses a fresh clock under the engine lock and
prioritizes earliest kernel expiry among due flows. Continuous coverage therefore
requires sufficient worker capacity and completion before the old 250 ms hard
deadline. Expiry never waits for that completion. Kernel last-seen counters
select active flows, not extend permission; idle flows are removed after 1 s.

Proposed authorization contract for integration
1. A full, successful existing resolver observation must prove the application,
   executable revision, user, Wine prefix/runtime, process generation, complete
   holders and socket evidence. No client-supplied application name or JSON hint
   can create a grant. A cookie distinguishes sockets; it never proves ownership.
2. Evaluate current policy under its normal serialization after verification.
   Only an actual Allow may publish a grant. Ask, Deny, ambiguous, incomplete,
   unsupported and expired evidence must use the ordinary enforcement path.
   A prior Allow on a different destination is not sufficient.
3. The initial experiment uses a 250 ms HARD maximum from the BEGINNING of full
   verification, with CLOCK_BOOTTIME/bpf_ktime_get_boot_ns including suspend.
   Publication after that deadline is refused. Hits and arrivals never extend it.
   A renewal needs a new complete observation and current Allow evaluation.
   This number is a prototype choice, NOT approval to deploy a reuse window.
4. Each kernel entry is restricted to the actual packet socket cookie and exact
   family/protocol/source/destination addresses and ports. Each map instance is
   private to one network namespace and one direction. No reverse authorization.
   Interface and authoritative zone classification must be validated for the
   packet, or the integration must refuse fast-path publication. A route/zone
   generation change invalidates certificates. Unsupported families, fragments,
   extension headers and packets without cookies use the normal path.
5. The userspace certificate also retains the exact verified app/user/prefix,
   revision and holder evidence. Another application sharing/transferring the
   SAME socket may use its grant until detected or expired: this is the explicit
   changed guarantee, bounded by 250 ms from verification start, not transfer.
   Socket close/replacement prevents cookie matching. Linux descriptor handoff,
   inheritance and Wine logical ownership are not all synchronously observable.
   No claim that a kernel hook identifies every Wine ownership transition.
6. A new policy/zone generation must invalidate kernel grants BEFORE successful
   mutation acknowledgement, coordinated with policy evaluation/publication.
   A failed map revocation must disable/remove the fast gate; failure to do so
   cannot be reported as a successful immediate revocation. Old grants still
   have their hard kernel deadline as a backstop, not as acknowledgement proof.
   Rule/lease expiry must shorten the grant deadline; relevant wall-clock changes
   need conservative invalidation. No permanent or once-only rule is lengthened.
7. A completed verification reporting changed/incomplete ownership removes the
   affected grant immediately; a stalled verifier cannot refresh it. Background
   renewal, retained entries and concurrent scans must have fixed bounds.
   Capacity exhaustion means normal-path enforcement, never an implicit Allow.
8. Fast acceptance must skip only FlowGate's attribution queue. It must still
   traverse existing accounting, priority and upload/download shaping hooks.
   Offer/refresh shaping bindings from verified identity using existing APIs.
   If binding/accounting preservation cannot be established for a configured
   mode, that mode cannot use the prototype fast path. This requires measured
   kernel enforcement evidence, not just a control-plane acknowledgement.

Hook being probed
An xt_bpf revision-1 match is installed by nft_compat directly in an owned IPv4
OUTPUT chain. FD_ELF uses the already-open socket-filter FD; the kernel holds its
reference. There are no bpffs pins, socket marks, conntrack permissions or shared
mangle chains. A successful BPF match followed by NF_ACCEPT terminates this
chain, not later netfilter/shaping hooks. A missing rule must leave normal queue
enforcement in place in the integration. The mechanism probe instead uses DROP
as its default to make unauthorized delivery observable without a daemon.

Expiry means the kernel authorization decision occurs before its deadline.
Packets already accepted can be buffered in qdiscs or the network and arrive
later. Report admission time and receiver delivery separately; do not claim
that a deadline can withdraw packets already sent or eliminate network delay.

Probe operation
check.py requires root to load BPF/netfilter in private PID/network/mount
namespaces. It emits only seven loopback UDP datagrams and has a 20-second child
deadline. Results and source/binary hashes stay under this checkout's .workspace.
Rules disappear with the private network namespace even on failure. BPF program
and link inventories are retained before/after, including one deferred-destruction
retry. No automatic cleanup of unexpected objects is performed. nft_compat/xt_bpf
may be globally auto-loaded by the kernel; they are not forcibly unloaded.
